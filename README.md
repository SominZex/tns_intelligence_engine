# TNS Agentic Retail Intelligent Chatbot

A production-oriented web application that exposes a **Databricks Genie
Agent** through a custom authenticated chat interface.

The application lets authenticated users ask natural-language business
questions and receive Genie-generated analytical answers, tables,
visualizations, reasoning, and suggested follow-up questions without
exposing the Databricks workspace directly to end users.

## Architecture

``` text
User
  |
  v
Custom Web UI
  |
  v
FastAPI Backend
  |
  +--> Authentication / CSRF / Rate Limiting
  |
  +--> PostgreSQL
  |      +--> Authentication sessions
  |      +--> Chat sessions
  |      +--> Chat messages + presentation metadata
  |
  v
Databricks OAuth
  |
  v
Databricks Genie Agent
  |
  +--> Natural-language reasoning
  +--> SQL / analytical execution
  +--> Query results
  +--> Visualizations
  +--> Suggested questions
  +--> Final analytical response
```

## Overview

This project is a custom analytics interface built around **Databricks
Genie Agent**.

Instead of requiring business users to interact directly with a
Databricks workspace, the application provides a dedicated chat
interface where authenticated users can ask questions such as:

> Forecast demand for Marlboro in the Delhi store for November and
> December 2026, weekly-wise.

The application forwards the request to the configured Genie Agent and
preserves the analytical response generated by Genie.

The custom application is responsible for the application layer:

-   authentication
-   CSRF protection
-   rate limiting
-   conversation persistence
-   secure Databricks communication
-   chat history
-   response rendering
-   query-result tables
-   visualizations
-   query-result downloads

The Genie Agent remains responsible for analytical reasoning, SQL
generation/execution, data analysis, forecasting where supported by the
configured Genie environment, and the final analytical response.

Users can ask business questions without writing SQL:

The backend communicates with the Databricks Genie Agent API and keeps

The UI can render:

-   final textual answers
-   reasoning/thoughts
-   query-result tables
-   visualizations

### Native Genie visualizations

When Genie produces a visualization, the backend retains the attachment

``` text
Genie visualization
       |
       v

       |
       v
Authenticated browser
       |
       v
```

Query attachments can be retrieved and represented as frontend tables

-   columns
-   rows
-   row counts
-   truncation information

The backend supports the full query-result download flow and returns

-   session expiration
-   logout

## Request Lifecycle

### New conversation

``` text
1. Browser sends question
2. FastAPI validates authentication
3. CSRF token is validated
4. Rate limiter is checked
5. Backend starts a Genie conversation
6. Genie processes the request
7. Backend waits for completion
8. Final answer is extracted
9. Native Genie attachments are processed
10. Application session is created
11. User and assistant messages are persisted
12. Structured response is returned to browser
13. Frontend renders the response
```

### Follow-up conversation

``` text
1. Browser sends message + application session ID
2. Backend retrieves the stored Genie conversation ID
3. Backend sends the message to the existing Agent conversation
4. Genie processes the follow-up using conversation context
5. Backend waits for completion
6. Response is extracted
7. Tables/charts/suggestions are processed
8. Message is persisted
9. Browser renders the response
```

This allows conversations such as:

``` text
User:
Show Marlboro demand for Delhi.

User:
Now forecast the next two months.

User:
Break that down week by week.

User:
What assumptions are driving the forecast?
```

## Databricks Genie Agent Integration

The application uses the Databricks Agent-mode response API
conceptually:

``` text
POST /api/2.0/genie/agents/{agent_id}/responses
```

Visualization generation is requested through the Agent response
configuration.

The Agent conversation identifier is persisted by the application and
reused for subsequent Agent-mode messages.

The application does not generate a second AI answer after Genie. It
transports and presents the Genie response.

## Agent Mode vs Legacy Chat Mode

This is an important architectural distinction.

Databricks exposes legacy Genie conversation APIs as well as newer
Agent-mode APIs. A legacy Chat-mode conversation cannot simply be sent
to the Agent responses endpoint.

The application therefore treats the conversation types separately:

``` text
Legacy Chat conversation
        |
        +--> cannot be used as Agent conversation

Agent conversation
        |
        +--> can be continued through Agent responses
```

Compatibility handling exists for application sessions that may contain
an older Genie conversation identifier. When necessary, the application
establishes a valid Agent-mode conversation rather than sending a legacy
conversation ID to the Agent endpoint.

## Response and Presentation Layer

The backend preserves native Genie response objects as much as possible.

A presentation can contain:

``` text
presentation
+-- blocks
|   +-- thoughts
|   +-- table
|   +-- visualization
|   +-- suggested_questions
|
+-- thoughts
+-- tables
+-- visualizations
+-- suggested_questions
+-- agent_message_id
```

The frontend renders these blocks in the order supplied by the backend.

This separates analytical responsibility from UI responsibility:

``` text
Genie
  |
  +--> analytical content
  |
  v
FastAPI
  |
  +--> response transport / attachment access
  |
  v
Frontend
  |
  +--> presentation
```

## Visualization Pipeline

Visualization retrieval is separate from the main answer path.

``` text
Agent response
      |
      +--> Final answer
      |
      +--> Query attachment
      |
      +--> Visualization attachment
                   |
                   v
          Databricks visualization
                   |
                   v
          FastAPI secure endpoint
                   |
                   v
                Browser
```

The application verifies that the requested Genie conversation belongs
to the authenticated application user before retrieving a visualization.

## Conversation Persistence

PostgreSQL is the application persistence layer.

### Authentication sessions

Conceptually:

``` text
auth_sessions
+-- session_id
+-- token_hash
+-- username
+-- created_at
+-- expires_at
```

The raw browser session token is not stored directly; its SHA-256 digest
is persisted.

### Chat sessions

The application maintains its own chat session and associates it with a
Databricks Genie conversation.

``` text
Application session
        |
        +--> Databricks Genie conversation
```

### Chat messages

Messages contain:

-   message ID
-   session ID
-   role
-   content
-   presentation metadata
-   timestamp

Presentation metadata allows rich responses to be reconstructed when
chat history is reopened.

## Authentication and Security

### Application authentication

Credentials are configured through environment variables. Passwords are
verified against a secure password hash.

### Browser sessions

After successful authentication, the application creates a random
browser session token. PostgreSQL stores only the token hash.

``` text
Browser
   |
   | app_session cookie
   v
FastAPI
   |
   | SHA-256(token)
   v
PostgreSQL
```

### CSRF protection

State-changing requests require a CSRF token obtained through:

``` text
GET /api/csrf
```

The frontend supplies the token using the configured CSRF header.

### Rate limiting

Separate rate limits are applied to sensitive operations such as login,
new chats, and follow-up messages.

### Databricks credentials

Databricks client credentials and OAuth access tokens remain on the
backend. They are never sent to the browser.

## Configuration

Configuration is loaded through Pydantic Settings and `.env`.

### Databricks

``` env
DATABRICKS_HOST=https://<workspace-host>
DATABRICKS_CLIENT_ID=<client-id>
DATABRICKS_CLIENT_SECRET=<client-secret>
GENIE_SPACE_ID=<genie-space-id>
```

### PostgreSQL

``` env
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
POSTGRES_DATABASE=<database>
POSTGRES_USER=<user>
POSTGRES_PASSWORD=<password>
POSTGRES_SCHEMA=genie_app
```

### Application authentication

``` env
APP_USERNAME=<application-user>
APP_PASSWORD_HASH=<password-hash>
APP_AUTH_SESSION_TTL_HOURS=12
APP_CHAT_SESSION_TTL_HOURS=24
```

### Cookie configuration

For local HTTP development:

``` env
APP_COOKIE_SECURE=false
APP_COOKIE_SAMESITE=lax
```

For HTTPS production:

``` env
APP_COOKIE_SECURE=true
```

### Genie execution

``` env
GENIE_POLL_INTERVAL_SECONDS=1
GENIE_TIMEOUT_SECONDS=300
```

Never commit `.env` or production secrets to Git.

## Design Principles

### Genie remains the analytical engine

The application does not try to replace Genie reasoning.

Databricks Genie remains responsible for interpreting questions,
generating/executing analytical queries, performing analysis, generating
forecasts where supported, producing visualizations, and generating the
final response.

The custom application is the secure delivery and persistence layer.

### Preserve native Genie output

The application preserves Genie response objects such as text, query
results, visualizations and suggested questions instead of flattening
everything into plain text.

### Separate critical and optional response paths

The final Genie answer is the primary response.

Charts and downloadable query resources are presentation enhancements. A
visualization retrieval problem should not unnecessarily invalidate an
otherwise valid analytical response.

### Keep credentials server-side

The browser communicates with FastAPI. FastAPI communicates with
Databricks. Databricks credentials never become frontend assets.

### Persist application state independently

The application owns authentication sessions, application chat sessions,
message history and presentation metadata.

Databricks owns Genie conversations and analytical execution.

This separation keeps application state independent from the underlying
analytics platform.

## Limitations

The application depends on the capabilities and configuration of the
connected Databricks Genie Agent.

Therefore:

-   analytical quality depends on the Genie Agent configuration and
    underlying data model
-   forecasting quality depends on the analytical capabilities and data
    available to Genie
-   visualization availability depends on whether Genie generates a
    visualization for a request
-   Databricks API availability and permissions are required
-   backend connectivity to Databricks is required
-   a legacy Chat-mode conversation cannot be converted into an
    Agent-mode conversation in place; a valid Agent-mode conversation
    must be used

The application does not independently validate the business correctness
of every SQL query or forecast produced by Genie. High-stakes business
decisions should be reviewed against the underlying data and business
definitions.

## Why This Architecture Matters

This project demonstrates a practical pattern for turning a Databricks
Genie Agent into a dedicated business analytics application.

Instead of exposing the analytics platform directly:

``` text
Databricks Workspace
       |
       v
   Genie Agent
```

the system creates an application layer:

``` text
Business User
       |
       v
Custom Analytics Application
       |
       v
FastAPI + PostgreSQL
       |
       v
Databricks Genie Agent
       |
       v
Business Data
```

The result is a conversational business-intelligence application
combining:

-   natural-language analytics
-   SQL-driven analysis
-   forecasting
-   analytical tables
-   visualizations
-   conversation context
-   persistent history
-   authenticated access
-   secure backend-to-Databricks communication
